# Portal Audit — Next.js admin/management portal (2026-06-06)

Area **Portal (Next.js)** from `AUDIT-PROGRAM.md` — internet-facing,
auth-bearing. Ran the playbook: 2 focused adversarial agents (auth/authz +
Next-version-specific; data/secrets/config), grounded in the installed Next
docs under `portal/node_modules/next/dist/docs/` (required by `portal/AGENTS.md`
— this is a non-standard Next 16.2.7 where the middleware file is `proxy.ts`),
then re-graded every finding.

## Scope

`portal/` — Next.js 16.2.7 App Router + Supabase auth (`@supabase/ssr`). Small
(~1.7k lines, much of it shadcn/ui). Security-relevant surface:
- `src/proxy.ts` + `src/lib/supabase/proxy.ts` — session middleware (auth)
- `src/lib/supabase/{server,client}.ts` — SSR/browser Supabase clients
- `src/lib/auth/roles.ts` — `getUserContext`, role model
- `src/app/{admin,bar}/{layout,page}.tsx` — gated routes + data fetches
- `src/app/login/actions.ts`, `login/page.tsx`, `signup/page.tsx`, `page.tsx`
- `next.config.ts`, `src/app/layout.tsx`

## Architecture (as found)

- **Auth** (`proxy.ts` → `updateSession`): validates the JWT server-side with
  `supabase.auth.getUser()` (not `getSession()` — correct), redirects
  unauthenticated users on non-public paths to `/login`. Authentication only.
- **Authz**: role gating in `admin/layout.tsx` (`isSuperAdmin`) and
  `bar/layout.tsx` (`hasAnyRole`); `page.tsx` (root) routes by role.
- **Data**: pages fetch with the **anon-key** Supabase client; row access is
  enforced by **Postgres RLS** (audited separately in Track A). **No
  service-role key anywhere** in the portal (confirmed by grep of `src` + env).

## Findings by tier (re-graded)

### HIGH

**H1 — Authorization lives only in layouts, not co-located with data access.**
`admin/page.tsx` / `bar/page.tsx` fetch fleet/bar data immediately with no
role check of their own — they trust `admin/layout.tsx` / `bar/layout.tsx`.
Next.js's **own** security guide
(`node_modules/next/dist/docs/01-app/02-guides/data-security.md`) explicitly
warns: *"be cautious doing checks in Layouts as these don't re-render on
navigation … do the checks close to your data source,"* and recommends a Data
Access Layer that performs the authorization check. With anon-key + RLS as the
only backstop, a layout that's skipped (partial RSC render, client-side nav
that preserves the layout, a future refactor) would let the page's fetch run
authorized solely by RLS. **Fix:** added `requireSuperAdmin()` / `requireAnyRole()`
DAL guards in `roles.ts` (mirroring the layout redirects) and call them at the
top of both pages. `getUserContext` is now wrapped in React `cache()` so the
layout gate + the page guard resolve the role queries **once** per request (no
extra DB round-trips). NB: not a forge-the-JWT issue — `getUser()` validates
the token; this is defense-in-depth per Next's documented guidance.

### MEDIUM

**M1 — No security headers (clickjacking / sniffing).** `next.config.ts` was the
empty boilerplate, so the admin panel shipped with no `X-Frame-Options` /
`frame-ancestors` (framable → clickjacking), no `nosniff`, no `Referrer-Policy`.
**Fix:** `next.config.ts` now sets `X-Frame-Options: DENY`, CSP
`frame-ancestors 'none'`, `X-Content-Type-Options: nosniff`,
`Referrer-Policy: strict-origin-when-cross-origin`, and a minimal
`Permissions-Policy`. Verified served via `next start` + `curl`. CSP is kept to
`frame-ancestors` only — a full `script-src` policy needs per-request nonces on
Next and would break the framework bootstrap + Supabase client (deferred).

**M2 — Open public signup.** `signup` (`login/actions.ts`) calls
`supabase.auth.signUp` with no invite/allowlist — anyone on the internet can
create an account. They land with no roles → `/no-access` (so **no data
access**, since every table is RLS-scoped and `hasAnyRole` gates `/bar`), but it
allows account/row spam and, via reflected auth errors, email enumeration. For a
B2B fleet portal this should be gated. **Deferred to a policy/owner decision**
(fastest: disable public signups in the Supabase dashboard, or add an
allowlist/invite flow — a real feature, out of scope for a hardening pass).
Flagged below.

### LOW

**L1 — Default boilerplate metadata** (`layout.tsx` was `"Create Next App"`).
**Fixed** → `"Table Wars Portal"` + `robots: { index: false }` (an internal
admin panel shouldn't be indexed).

**L2 — No `.env.example`.** The anon URL/key are public-by-design and `.env*` is
correctly gitignored + untracked (no secrets in the repo), but there was no
template. **Fixed** — added `.env.example` (with a "never put the service-role
key here" note) and a `!.env.example` gitignore exception.

**L3 — Reflected auth error messages** (`login/actions.ts`) can leak account
existence ("user already registered"). React escapes the rendered text (no XSS),
and `encodeURIComponent` guards the URL. Best mitigated by Supabase's
"prevent email enumeration" project setting rather than client-side string
munging (which harms login UX). Noted for the owner; not code-fixed.

## Re-graded DOWN / rejected

- **"CRITICAL: attacker spoofs JWT role to super_admin"** — false. JWTs are
  signed by Supabase and validated server-side via `getUser()`; they can't be
  forged. The real H1 concern is layout-skip yielding RLS-scoped data, not role
  forgery — graded HIGH, not Critical.
- **"CSRF on server actions unclear"** — not a finding. Next 16 server actions
  are POST-only and **compare Origin to Host/X-Forwarded-Host**, aborting
  cross-site invocations (`data-security.md:544`); `@supabase/ssr` cookies are
  httpOnly/secure/SameSite by default. Framework-handled.
- **"Privilege escalation org-vs-location / forge location claim"** — relies on
  forging a JWT or an RLS bug; the portal correctly derives roles from DB tables.
  An RLS concern (audited separately), not a portal-code defect.
- **"Add explicit `.in(locationIds)` filters in `bar/page.tsx`"** — declined.
  RLS is the audited, authoritative row scope and correctly models transitive
  org→location access; duplicating it in the page risks **drift** (an org_admin
  legitimately sees multiple locations). The right portal-side fix is the H1
  role-presence guard + trusting audited RLS for row scoping.

## Verified solid (keep)

- `getUser()` not `getSession()` in the proxy (server-side JWT validation).
- **Anon-key only** — no service-role client anywhere; `.env*` gitignored +
  untracked; no secrets in source or history.
- No `dangerouslySetInnerHTML` / `eval` / raw HTML; React auto-escaping; reflected
  `searchParams.error` rendered as escaped text.
- Server-action CSRF handled by the framework (Origin/Host check).
- Sensible role model + redirects; root `page.tsx` role routing.

## Deliberately deferred (with rationale)

- **Invite-gate / disable public signup (M2)** — policy + feature; fastest path
  is the Supabase dashboard toggle (owner action).
- **Full `script-src` CSP** — needs Next nonce plumbing; risks breaking the app.
  Shipped the high-value framing/sniff/referrer headers now.
- **Email-enumeration hardening (L3)** — Supabase project setting.

## Manual follow-ups (owner)

1. In the Supabase dashboard: **disable public sign-ups** (or add an allowlist)
   and enable **"prevent email enumeration"** — addresses M2 + L3 without code.
